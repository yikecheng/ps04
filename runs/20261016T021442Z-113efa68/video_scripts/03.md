## Scene 1 — Choose a reversible first task

**Narration**

<!-- claim:03-c1 -->
Treat coding-agent adoption as an engineering experiment you can reverse. Start with one narrow task class: for example, default-branch CodeQL remediation or a well-established deterministic transformation. GitHub defines the first workflow tightly, while the Android Bench account reports stronger results on the second category. AgentSWE’s gap between demonstrated and held-out performance is a reason to exclude open-ended agent construction from the first pilot.

## Scene 2 — Write acceptance before execution

**Narration**

<!-- claim:03-c2 -->
Before the agent runs, convert the brief into explicit acceptance clauses and reserve at least one check the agent never sees. If the requirement is ambiguous, run a structured questioning pass before implementation. AgentSWE motivates the hidden check: it freezes a delivery before held-out evaluation. The supervision study emphasizes planning, while a GitHub Copilot Day demonstration illustrates using structured questions to align the work.

Make acceptance observable: name the expected behavior, forbidden behavior, test boundary, and required evidence. A passing visible example should be an input to the decision—not the entire decision.

**Visual direction**

[VISUAL: Acceptance card with four fields: Expected behavior; Must not happen; Visible checks; Hidden check. Animate questions being resolved before the card moves to “Ready.”]

**Source notes — video 0:45–1:30**

GitHub Copilot Day media evidence appears at source timestamps 2:41–2:45 and 3:52–3:55. The complete acceptance pattern is a synthesis, not a tested recipe from one source.

## Scene 3 — Isolate work, ownership, and cost

**Narration**

<!-- claim:03-c7 -->
Run concurrent agents in separate worktrees and make status and ownership visible. OpenAI’s Codex CLI demonstration shows visible running status, grouping by status, and context forking. Treat checkout isolation as containment, however—not proof that two changes are semantically compatible or safe to merge.

<!-- claim:03-c5 -->
For GitHub agentic autofix, one pull request may include up to 25 selected code-scanning alerts. That is a product ceiling, not a recommendation to begin at the ceiling.

<!-- claim:03-c6 -->
GitHub also says the workflow consumes AI Credits from the Code Security budget and GitHub Actions minutes. Put both into the pilot budget before deciding whether the workflow saves total effort.

**Visual direction**

[VISUAL: Two isolated worktree boxes feed separate draft PRs. Above them, a small board shows Owner, Running, Review, and Blocked. Add a cost counter for AI credits and Actions minutes.]

**Source notes — video 1:30–2:20**

OpenAI media evidence appears at 1:34–1:36, 1:37–1:38, 1:56–1:58, and 2:00–2:01. Worktree containment does not resolve semantic conflicts.

## Scene 4 — Keep approval, rollout, and rollback gates

**Narration**

<!-- claim:03-c3 -->
Keep agent-authored fixes behind human pull-request approval. Then deploy progressively with an editable monitoring plan and a tested rollback path. Cursor exposes those control points through Rollouts, while GitHub’s security workflow produces a draft PR. Spotify’s reported check-passing production failure is the reason not to collapse these gates into one approval.

<!-- claim:03-c4 -->
For migrations, replace components incrementally behind a temporary compatibility boundary. InfoQ reports that GitHub used that pattern during its TypeScript-to-Rust migration, allowing existing end-to-end tests to exercise each replacement while other components remained in TypeScript.

**Visual direction**

[VISUAL: Gate sequence: Draft PR → Human approval → Progressive rollout → Monitor → Continue or Revert. Then show old and new components connected by a temporary bridge, with end-to-end tests crossing both sides.]

**Source notes — video 2:20–3:10**

Cursor and GitHub provide product workflow evidence. The migration and Spotify incident are company accounts reported by InfoQ and come from organizations much larger than the target team.

## Scene 5 — Measure accepted outcomes, then decide

**Narration**

<!-- claim:03-c8 -->
Score the pilot on accepted outcomes and full supervision cost: held-out pass rate, rework, reviewer time, rollout or rollback events, credits, and tokens. Do not treat pull-request or code volume alone as success. Throughput can rise while review burden, complexity, or unobserved risk moves elsewhere.

<!-- claim:03-c9 -->
The next persuasive external signal is convergent improvement in frozen held-out acceptance, one-attempt resolution, cross-module harness behavior, and runtime-heavy tasks. A higher aggregate leaderboard position by itself is not enough.

No source tests this entire pilot design end to end. Hidden tests, staging, and observability may be costly for a very small team. The migration and maintenance examples come from unusually large organizations, and worktree isolation cannot prevent semantic conflicts. That lack of independent outcome evidence should constrain autonomy; it does not show that agents have no value.

The decision rule is simple: expand only when your own accepted outcomes improve after counting supervision and recovery costs.

## Ready-to-paste companion-article copy

**Headline:** A practical small-team pilot for coding agents

**Standfirst:** Choose one reversible task, specify acceptance before execution, isolate concurrent work, retain approval and rollback gates, and count supervision as part of the cost. Expand only when accepted outcomes—not generated code—improve.

**Callout:** Adoption should be a reversible experiment with an explicit stop condition.

## Ready-to-paste video-description copy

This Agent Signal field guide turns current coding-agent evidence into a controlled adoption sequence for teams of 2–20 people: choose one bounded task, write acceptance clauses and a hidden check, isolate execution, require human review, deploy progressively, preserve rollback, and measure total supervision cost.

The design is a synthesis rather than a proven end-to-end recipe. Expansion should follow your team’s accepted outcomes and stronger independent evidence on held-out, cross-module, and runtime behavior. Evidence cut-off: October 16, 2026.
