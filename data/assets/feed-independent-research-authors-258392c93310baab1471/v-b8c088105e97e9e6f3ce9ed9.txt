AgentSWE: Can Coding Agents Build the Agent You Actually Want?

As the production of software passes into the hands of software itself, coding agents are increasingly commissioned to build agents fitted to their users’ own workflows. This delegation carries a quiet assumption, that the delivered agent will faithfully serve the requirement it was built for, rather than merely appear to. No existing benchmark tests that assumption. We introduce AgentSWE , a benchmark for agent software engineering spanning three stages of the agent development lifecycle: Creation of a complete agent from a natural-language requirement, Editing of production agent codebases, and Optimization toward a measurable target. Each of its 25 tasks is framed as a commission rather than an exam: the builder iterates against a handful of illustrative cases, while acceptance exercises the frozen submission on held-out cases designed to span the full requirement, grading behavior against requirement-derived rubrics under hard pass/fail gates or, for Optimization, against the source benchmark’s own objective. Evaluating a range of coding agents across models and harnesses, we find that none comes close to delivering what a requirement asks for: the gap between what a builder demonstrates and what it delivers is the norm, not the corner case. An accompanying empirical analysis of the failure trajectories identifies recurring failure modes, among them overfitting to the visible cases, hollow runtimes behind code that looks complete, and unsupported claims of completion, each a signal by which coding agents can learn to build the agents they are asked for.

Coding agents such as Claude Code ( Anthropic, 2026 ) and Codex ( OpenAI, 2026a ) now carry substantial engineering workloads ( Chen et al., 2021 ; Yang et al., 2024b ; Wang et al., 2025b ) , and many of their users are not engineers: they describe what they need and delegate the rest ( Hitzig et al., 2026 ) . Increasingly, what they delegate is the building of an agent, a program that wraps a model, tools, and state around one recurring job so that the job runs on a fixed runtime, at a fixed cost, without a coding agent attending each run. Delegation of this kind rests on trust: that a coding agent, handed a requirement in natural language, will deliver the agent its user intends rather than one that merely appears to comply. Whether that trust is warranted is what this paper measures.

Agent development spans three stages. It begins with creation , where a natural-language requirement must become a working system; continues through editing , where new capabilities join a living codebase without unsettling what already works; and matures into optimization , where the agent is pushed toward an explicit target, be it a public leaderboard or a production workload. Handing this lifecycle to coding agents invites failures subtler than broken code: an agent that passes visible examples yet misses the intent behind them ( Liu et al., 2023 ; Zhao et al., 2026a ; Lodkaew et al., 2026 ) ; a tool registered but never invoked ( Soni, 2026 ; Fan et al., 2026 ) ; a goal that drifts over a long horizon ( Arike et al., 2025 ; Menon et al., 2026 ) ; a report citing evidence no source contains ( Onweller et al., 2026 ; Rao et al., 2026 ) . Such failures are not hypothetical; they are the present condition of agent-built agents ( Raj et al., 2026 ; Naik et al., 2026 ) . The questions are how far coding agents compromise the requirements they are handed, on which capabilities, and for what reasons.

These questions outrun the instruments we have. SWE-bench and its descendants grade the repair of conventional software against a reference patch or test suite ( Jimenez et al., 2024 ; Chan et al., 2024 ) ; NL2Repo-Bench commissions whole repositories from requirement documents ( Ding et al., 2025 ) ; Paper2Code and PaperBench rebuild research implementations checked against the papers they reproduce ( Seo et al., 2025 ; Starace et al., 2025 ) . Each judges ordinary code against an answer known in advance. A commissioned agent wraps a stochastic policy around tools, answers to a requirement that has no reference solution, and keeps changing after delivery. Benchmarks that do evaluate agents, from AgentBench onward ( Liu et al., 2024 ) , examine a finished agent and ask how well it performs; none asks whether a coding agent could have built it. Work on agents that design or improve other agents ( Hu et al., 2025 ; Mishra et al., 2026 ) comes closest, but it measures how far a search procedure or a meta-agent can raise a benchmark score, not whether a general coding agent delivers the agent a requirement describes ( Section 2 ). Between judging built software and judging finished agents lies a step that current suites leave unmeasured: building the agent that a requirement asks for.

We introduce AgentSWE , a benchmark that turns faithful delegation from anecdote into measurement ( Figure 1 ) through three commitments. The first is to measure the whole lifecycle, through twenty-five tasks spanning all three stages. Ten Creation tasks commission a complete agent from a natural-language requirement, over workloads from GUI automation to formal theorem proving, each scoped against a mature open-source system; ten Editing tasks ask for new capabilities in the pinned codebase of a production agent such as OpenHands or Aider, capabilities that cut through crash recovery, permission fencing, and transactional state; and five Optimization tasks set a working agent against a measurable target. The second commitment is that evaluation should mirror the delegation it studies. Each task is framed as a commission: the builder sees only what a customer could provide, while acceptance also tests the stated clauses its examples leave out. The builder develops against the requirement and a few illustrative cases; held-out cases then test the frozen delivery in isolation. The third commitment follows from the absence of a prescribed reference implementation: every Creation and Editing execution is graded against a rubric derived from the requirement itself, and hard gates assign zero to invalid executions and inapplicable patches.

We put this instrument to work on five models as builders in the Codex harness, together with further pairings of harness and model. The verdict is sobering. The strongest builders average 19.1 on Creation and 31.6 on Editing, and in Optimization no builder closes more than 5 % of the remaining gap to the target on average, and only 13 of the 25 runs score above their starter. Creation runs that end development at 90 or above deliver agents averaging 9.9 on held-out cases. The gap between what a builder demonstrates and what it delivers is not the corner case of agent software engineering; it is the norm. The builders’ trajectories reveal recurring failures. Builders overfit to the visible development cases, and the delivery fails on the clauses those cases leave out; they ship hollow runtimes, code that reads as complete but does no work when run; and both builders and the agents they deliver claim completions that their own records contradict. Each of these modes names a habit that the next generation of coding agents can be built and trained to avoid. More development cases, a prescribed design, an instruction to test, and a longer case budget shift the scores but leave held-out Result low under every condition.

In sum, this paper makes three contributions. First, we formalize agent software engineering as a measurable problem, in which a builder must satisfy a requirement it can probe only through limited development feedback. Second, we deliver AgentSWE, twenty-five commissions whose acceptance executes the delivered agent on held-out cases and grades each run with a requirement-derived rubric or a native objective, and we evaluate various harness–model pairings against it. Third, we contribute an empirical analysis of the failure trajectories, which identifies recurring failure modes of coding agents and turns each into a direction for the next generation of coding agents.

2 Related Work

Agents that build and optimize agents.

Research on automated agent development has expanded both the scope of what can be designed and the stage at which adaptation occurs. Early approaches generate task-specific roles, tools, and collaboration patterns from task descriptions or seed agents ( Chen et al., 2024 ; Yuan et al., 2025 ; Tang et al., 2026 ) . Subsequent work formulates agent development as optimization, first over textual components such as instructions and demonstrations ( Yang et al., 2024a ; Khattab et al., 2023 ; Agrawal et al., 2025 ) , and then over broader design spaces containing agent modules, communication structures, and executable workflows ( Zhuge et al., 2024 ; Shang et al., 2025 ; Zhang et al., 2025c ; Zhang et al., 2025a ; Zhou et al., 2025 ) . This paradigm has further expanded to searching over complete code-defined agents and multi-agent scaffolds ( Hu et al., 2025 ; Rosser & Foerster, 2025 ) .

A related line relaxes the assumption that the improvement procedure itself remains fixed. Initial systems support self-referential modification of an improver or agent logic ( Zelikman et al., 2023 ; Yin et al., 2025 ) , while later approaches expose complete implementations, harnesses, and meta-level improvement mechanisms to revision ( Robeyns et al., 2025 ; Zhang et al., 2025b ; Wang et al., 2025a ; Zhang et al., 2026b ; Lee et al., 2026 ; Hebbar et al., 2026 ) . Arbor ( Jin et al., 2026 ) carries hypotheses and evidence across long-horizon artifact optimization, whereas JIT-Agent ( Zhang et al., 2026a ) synthesizes task-conditioned executable harnesses at inference time. Together, these developments establish agent construction and optimization as a capability in its own right. AgentSWE makes this capability the object of evaluation, measuring whether general-purpose coding agents can create, modify, and optimize agents from heterogeneous user requirements.

Benchmarks for agent construction.

Most agent benchmarks hold the agent implementation fixed and evaluate its performance within a given environment. Recent benchmarks move beyond task completion by asking agents to construct or iteratively improve more complex artifacts. WorFBench ( Qiao et al., 2025 ) evaluates generated workflow structures, while benchmarks for machine-learning experimentation and research engineering evaluate improvement of executable research artifacts ( Huang et al., 2024 ; Nathani et al., 2025 ; Wijk et al., 2025 ) . AI4AI-Bench ( Chi et al., 2026 ) extends this setting to the redesign of model-training algorithms. Other evaluations isolate specific improvement mechanisms: SE-Bench ( Yuan et al., 2026 ) studies knowledge internalization, whereas OPT-BENCH ( Li et al., 2026 ) measures feedback-driven solution refinement. These benchmarks evaluate workflows, research artifacts, or optimized solutions rather than deployable agents.

Closest to our setting, AIE-Bench ( Mishra et al., 2026 ) evaluates whether a meta-agent can improve a pinned target-agent scaffold under controlled mutation boundaries and trial budgets. AgentSWE extends this setting to the full agent-development lifecycle: creating agents from natural-language commissions, modifying existing agent codebases without regression and optimizing working agents toward measurable objectives. By freezing submissions and evaluating their behavior on held-out cases, AgentSWE measures whether coding agents can deliver the agents users actually request.

3 Problem Formulation

A commission prescribes no reference implementation, so we define the requirement, the delivered agent, the builder, and the fidelity of a delivery through observable behavior alone.

A commission begins with a natural-language requirement q = ( g , ℐ , 𝒞 , ℛ ) q=(g,\mathcal{I},\mathcal{C},\mathcal{R}) , which every AgentSWE task publishes in four parts: the goal g g , which states what the agent is for and what counts as serving its user; the interface contract ℐ \mathcal{I} , which fixes how the agent is launched and which artifacts it must deliver; the constraints 𝒞 \mathcal{C} , which bound what may be edited, installed, or invoked; and the resources ℛ \mathcal{R} , such as data, repositories, and access to models and search. A case x x is one concrete instance of the commission. The requirement comes with a small set D D of public development cases, while the cases that matter, the ones the delivered agent will face in use, remain unwritten; we write 𝒳 q \mathcal{X}_{q} for the space of cases the requirement implies.

The deliverable is itself an agent a = ( h , m ) a=(h,m) : a harness h h , the orchestration code that plans, routes, and retries ( Raj et al., 2026 ; Lee et al., 2026 ) , around a backbone model m m reached through a fixed gateway. Executing a a on a case x x in environment E E yields observable outcomes y ∼ a ⁡ ( x , E ) y\sim a(x;E) . Because m m samples, the same delivery may satisfy a requirement on one execution and betray it on the next, so acceptance executes the agent and grades what it does.

A coding agent, or builder , is an agent β \beta whose actions are software engineering: reading a requirement, exploring and editing a workspace, running what it wrote, and deciding what to try next ( Yang et al., 2024b ; Wang et al., 2025b ) . Handed a commission, the builder produces an artifact a ^ ∼ β ⁡ ( q , a 0 , D , B ) \hat{a}\sim\beta(q,a_{0},D;B) , where a 0 a_{0} is the initial artifact, possibly empty, D D the development cases it may probe freely, and B B a budget on time and compute.

The customer cares about how faithfully a ^ \hat{a} serves the requirement on cases it has not seen. We estimate fidelity on a held-out set D ¯ ⊂ 𝒳 q \bar{D}\subset\mathcal{X}_{q} , disjoint from D D and designed to exercise the promises in g g , graded by a rubric that realizes μ q \mu_{q} . Writing F D F_{D} and F D ¯ F_{\bar{D}} for the estimates on the development and held-out cases, the gap between demonstrated and delivered fidelity, F D − F D ¯ F_{D}-F_{\bar{D}} , measures how much better the delivered agent does on the cases the builder saw than on the cases it did not.

3.3 Task Families

The three lifecycle stages are instances of Definition 3.1 that differ in the initial artifact a 0 a_{0} and in the shape of μ q \mu_{q} .

Creation ( a 0 = ∅ a_{0}=\emptyset ).

The builder starts from an empty workspace and must deliver a complete agent under the interface contract ℐ \mathcal{I} ; fidelity is estimated on held-out cases as in Equation 1 .

Editing ( a 0 = a_{0}= a production system).

The initial artifact is the pinned codebase of a working agent product, and the requirement commissions new capabilities. The constraints 𝒞 \mathcal{C} confine the builder’s changes to an authorized region, and satisfaction has two parts,

the commissioned behavior μ new \mu_{\mathrm{new}} and the preservation μ reg \mu_{\mathrm{reg}} of everything the product already did, checked by its public suite and published contracts ( Jimenez et al., 2024 ) .

Optimization ( a 0 = a_{0}= a working agent).

The initial artifact already satisfies the interface, and the requirement names a measurable objective J J on a 0–100 scale, whose ceiling J ⋆ = 100 J^{\star}=100 is the target. Delivery is judged by the fraction of the remaining gap to the target that the builder closes ( Wijk et al., 2025 , cf.) ,

on held-out instances of the objective.

4 The AgentSWE Benchmark

AgentSWE turns Definition 3.1 into 25 commissions: ten Creation, ten Editing, and five Optimization tasks. Each task hands a coding agent, the builder, a requirement q q , an initial artifact a 0 a_{0} , and development cases D D , and grades the agent it delivers on held-out cases. Figures 2 and 3 show how tasks are built and evaluated; Appendix B walks through one task per family.

4.1 Task Construction

Each family fixes the requirement q q and the initial artifact a 0 a_{0} in its own way ( Figure 2 a). In every family, GPT-5.6 Sol ( OpenAI, 2026c ) drafts the task materials from the analyzed source system, and the authors verify and refine each draft. Creation tasks come from open-source domain agents on GitHub, in domains from desktop automation and scientific PDF translation to formal theorem proving. Each repository is reverse-engineered into a self-contained goal and a set of functional requirements, extended with capabilities that broaden its purpose and raise the compositional difficulty, and published as input Markdown files that state the goal, interface contract, constraints, and resources of q q ; the initial artifact is empty.

Editing tasks extend a pinned repository snapshot a 0 a_{0} of five general-purpose coding agents and five domain agents, among them Claude Code ( Anthropic, 2026 ) , Aider ( Gauthier, 2026 ) , OpenHands ( Wang et al., 2025b ) , and OpenClaw ( OpenClaw Contributors, 2026 ) . The commissioned capabilities come from design brainstorming or from unresolved issues in the repository; we keep proposals with a consequential user need, a bounded implementation surface, and behavior that execution can verify, and write each as a feature specification with an acceptance boundary and the regression obligations that a 0 a_{0} already carries.

Optimization tasks build on BrowseComp ( Wei et al., 2025 ) , τ 3 \tau^{3} ( Yao et al., 2024 ; Barrès et al., 2025 ) , TerminalBench ( Merrill et al., 2026 ) , PinchBench ( Kilo AI, 2026 ) , and OSWorld ( Xie et al., 2024 ) and keep their native task definitions. Each ships a starter agent as a 0 a_{0} ( Table 6 ), and the requirement names the objective, the files the builder may edit, and the runtime resources it may not change.

4.2 Task Package

Each task separates what the builder sees, namely q q , a 0 a_{0} , and the development cases D D , from what evaluation reserves ( Figure 2 b). Every Creation and Editing task publishes two development cases, which demonstrate the entry point, the delivery contract, and a small part of the required functionality; Optimization draws a development split from the instance pool of its source benchmark.

Evaluation reserves the held-out cases and the scoring contract. Each Creation and Editing task holds out six cases. Each case exercises one or more requirement clauses, among them clauses and capability interactions that the requirement states but the development cases leave out, and together the six cover diverse inputs, state, and data. Optimization holds out a disjoint split of the same pool. In total the suite has 150 development and 365 held-out cases. The scoring contract of a Creation or Editing task is a task-specific Result rubric whose weighted items derive from the functional requirements, with gates and ceilings for violations of the interface contract and the constraints ( Appendix C ); Optimization keeps the native evaluator of its source benchmark. Held-out inputs, evaluator state, scoring contracts, credentials, and model routing never enter the builder’s workspace, and the builder receives feedback only on its development cases.

4.3 Evaluation Protocol

Development and freezing.

Harbor ( Harbor Framework Team, 2026 ) , a container framework for agent evaluation, runs the builder in one persistent session ( Figure 3 , left). The builder works in a private writable workspace and may submit a snapshot of its delivery at any time. Each snapshot runs on the development cases in isolated jobs, and the scores and summarized feedback return to the same session, within fixed time and submission budgets ( Appendix E ). Development ends when the builder exits or exhausts its submissions or its time budget. Creation then freezes the workspace; Editing freezes the last accepted submission, so a builder whose submissions were never accepted delivers nothing; Optimization freezes the accepted snapshot with the highest development objective. Freezing records the delivery and its software environment, and the held-out evaluation verifies that neither has changed.

Each held-out case runs the frozen delivery through its fixed entry point in an isolated, pinned runtime ( Figure 3 , right; Appendix D ). Every model call the delivered agent makes goes through a benchmark-owned gateway to one runtime model, shared by all deliveries in a task family, so that the score reflects what the builder contributes: prompts, tool orchestration, context and state management, and output validation.

For Creation and Editing, deterministic gates first assign zero to an execution that does not launch, exceeds its time budget, or produces no parseable deliverable. A frontier reasoning model at its highest effort then applies the Result rubric ( Zheng et al., 2023 ; Arora et al., 2025 ) (GPT-5.6 Sol for Creation, DeepSeek-V4.1-Flash ( DeepSeek-AI, 2026b ) for Editing; Table 9 ). The judge grades what the agent produced on one concrete case, its artifacts, execution trace, and resulting state, rather than the quality of its code, and ceilings bind the score to the violations the evaluator records. The task score is the mean partial-credit score over its held-out cases on a 0–100 scale, and family scores are macro-averages over tasks. Optimization instead scores the selected candidate and the starter with the native evaluator on the same held-out instances, a signal independent of the Result judge, and reports the gap closure of Equation 3 .

Section 5.2 measures held-out performance, Section 5.3 analyzes the trajectories of these runs and the failure modes they reveal, and Section 5.4 examines how held-out Result and these failures respond when the conditions of the build change or the build is repeated.

The main comparison evaluates five builders that pair the Codex harness with GPT-5.6 Sol, GPT-5.5 ( OpenAI, 2026b ) , DeepSeek-V4-Pro, DeepSeek-V4-Flash ( DeepSeek-AI, 2026a ) , and Qwen3.6-35B-A3B ( Qwen Team, 2026 ) ; we refer to each builder by its model. A run is one builder developing one task, from the commission to the frozen delivery. Creation and Editing report the mean Result over the six held-out cases of each task. Optimization reports gap closure S = 100 ​ γ S=100\gamma ( Equation 3 ), computed from the change Δ = J ⁡ ( a ^ ) − J ⁡ ( a 0 ) \Delta=J(\hat{a})-J(a_{0}) in the native objective on the held-out split; S S is negative when the candidate scores below its starter. 5.2 Held-out Performance

Creation success is rare and task-specific.

The 50 Creation runs in Table 1 average a Result of 11.2 (median 3.4), and 20 of them score zero. The highest-scoring builder, DeepSeek-V4-Pro, averages 19.1 yet scores below 20 on eight of ten tasks. Only three runs exceed 50, all on formal theorem proving or repository bug repair, and no builder exceeds 30 on more than one task. Success on one commission does not carry over to the next, and none of the evaluated builders reliably builds the agents that AgentSWE specifies.

Editing yields partial capabilities, or no delivery at all.

The builders that deliver on nearly every task, DeepSeek-V4-Pro, GPT-5.5, and GPT-5.6 Sol, still realize only part of the commissioned capabilities: their means lie between 20 and 35, and only one run, GPT-5.5 on the Codex task, reaches 70. Qwen3.6 fails earlier: it submits no candidate on any task, typically ending its session right after announcing a plan. DeepSeek-V4-Flash delivers on four tasks; on most of the others it works until the budget runs out without ever submitting a candidate. Adding capabilities to a working product thus fails in two ways: the patch covers only part of the requirement, or the builder never finishes one.

Optimization gains are inconsistent across tasks.

No builder closes more than 5 % of the remaining gap to the target on average. Of the 25 runs, 13 score above the starter, nine below it, and three match it; under a per-run sign test, five runs differ from their starter: three BrowseComp gains and two losses, on τ 3 \tau^{3} and PinchBench ( Section G.3 ). Gains depend on the task: on BrowseComp four of five builders score above the starter, whereas on PinchBench four of five score below it.

5.3 Trajectory Analysis and Failure Modes

Analyzing the builders’ trajectories, the frozen artifacts, and the delivered agents’ execution traces in the main runs, we find three recurring failure modes ( Appendix H gives the protocol).

Overfitting to the visible cases.

Development scores overstate what a delivery does on the rest of the requirement, so the gap F D − F D ¯ F_{D}-F_{\bar{D}} of Section 3.2 is wide. Eleven Creation runs end development with a score of at least 90, yet their held-out Result averages 9.9; one of them hard-codes its two development cases ( Appendix I ). A DeepSeek-V4-Pro Editing delivery scores 100 on development cases and 28.3 on held-out cases. In Optimization, the selected candidate gains 13.1 points on development cases but only 1.8 on held-out cases ( Section G.4 ), although both splits come from one instance pool; on four of the five benchmarks the gains shrink or reverse ( Figure 6 ).

Trajectories and artifacts reveal case-specific implementations: builders fit their agents to the visible cases in 14 of 25 Optimization runs and 13 of the 33 Editing runs that deliver. On PinchBench, DeepSeek-V4-Flash and DeepSeek-V4-Pro route tasks by keyword to playbooks for visible task categories, gaining 8.1 and 59.4 points on development cases and losing 15.2 and 15.1 on held-out cases ( Appendix I ). Even explicit feedback leaves such defects unresolved: in eight of ten DeepSeek-V4-Pro Editing runs, development feedback names a violated requirement that the delivery still violates on held-out cases ( Section H.3 ). The requirement states what the held-out cases test; what fails is translating a requirement with interacting capabilities into an agent that generalizes beyond the visible cases.

Code that reads as complete often does not work when run. In Creation the failure is loud: 157 of the 270 traced held-out executions (58.1 %) fail a validity gate, nearly all by exiting with an error or timing out ( Figure 6 ). Yet a static review of every frozen Creation source, by the same judge as Result on an eight-dimension rubric ( Section G.1 ), does not separate deliveries with zero Result from the rest ( Figure 6 ): apart from Qwen3.6, lowest on both, deliveries with zero Result score 44.2 and those with nonzero Result 45.8.

In Editing, 28 of the 33 runs that deliver leave some added capabilities absent, uninvoked, or incompletely executed ( Sections H.3 and I ). These failures can be silent: an OpenWiki delivery passes every validity gate yet leaves four of its five required output categories empty on every held-out case.

Unsupported claims of completion.

Reports of success are unreliable at both levels of the delegation. Checked against the builder’s own trajectory, artifact, and feedback, 6 of the 42 final Creation reports and 3 of the 19 Optimization reports claim completions that these records contradict ( Table 13 ; Appendix I ). All nine assert completion; no report that admits partial failure is contradicted. Delivered Editing agents overclaim at run time too: in 13 of the 33 runs that deliver, they report outcomes that their own effect logs or state contradict, and the OpenWiki delivery above declares its run complete.

Scores rise from zero to two development cases, not beyond.

Development cases are what builders overfit to ( Section 5.3 ). On two Creation tasks, with three builder runs per condition, we give the builder zero, one, two, or four of them. Going from zero to two development cases raises mean Result by 34.3 points on PDF translation and by 29.3 on PPTX generation ( Table 4 ); without any case, all three PDF deliveries score zero. Two further cases add nothing on PDF and lower PPTX from 33.5 to 15.2 ( Figure 7 ).

A prescribed design lowers PPTX; self-testing narrows its spread.

We also append one of two prompt priors to the builder instruction ( Section D.1 ). Strategy A prescribes a design, the components and how they connect; Strategy B asks the builder to write additional cases and run its agent end to end, aiming at the hollow runtimes and unsupported claims of Section 5.3 . Strategy A leaves PDF unchanged and lowers PPTX from 29.6 to 7.4; Strategy B raises PDF from 39.2 to 48.9, within run-to-run variation, and leaves the PPTX mean unchanged while narrowing its spread ( Table 4 ).

The gap remains with 2.5 times the case budget.

Only 15 of the 270 held-out Creation executions in the main runs reach the 600 s limit ( Figure 11 ). Rebuilding all ten Creation tasks with 1,500 s per case and a requirement for a traced runtime agent ( Section E.2 ) leaves both failure modes in place: no execution reaches the limit, the last development score exceeds held-out Result on every task, 70.3 against 31.5 on average ( Table 10 ), and a third of the held-out executions produce no valid result.

Scores vary across harness–model pairings.

With the model held fixed, scores differ across harnesses ( Table 4 ): on scientific PDF translation, GPT-5.5 scores 21.8 under Codex and 42.8 under OpenCode, and DeepSeek-V4-Flash 5.8 under Claude Code and 30.5 under DSH. No harness leads for every model, so we evaluate pairings of harness and model, not models alone.

The same pairing delivers very different agents across builds.

The main comparison and harness studies build each pairing once. On eight tasks from the three families, we build each of three builders three times under fixed conditions ( Table 5 ; Section E.2 ). Builds of one pairing can lie far apart ( Figure 8 ): GPT-5.6 Sol scores 32.8, 33.3, and 90.5 on DeepTutor, and DeepSeek-V4.1-Flash 0.0, 33.3, and 56.8 on repository bug repair. No builder leads on every task, and Qwen3.6 averages at most 6.0 on any task. Overfitting recurs: two GPT-5.6 Sol builds of database analytics reach 99 on the development cases and 11.0 and 6.5 on held-out cases ( Section 5.3 ). The repository provides these eight tasks and this configuration as AgentSWE-Lite, a lower-cost entry point for evaluation.

We introduced AgentSWE to measure whether coding agents deliver agents that serve their requirement on cases they have not seen. Current builders rarely do: in the main comparison, the strongest average 19.1 on Creation and 31.6 on Editing, and in Optimization none closes more than 5 % of the remaining gap to the target on average. The trajectories reveal recurring failures: builders fit the visible cases, ship runtimes that read as complete but do not work, and, like the agents they deliver, claim completions their own records contradict. These failure modes chart where coding agents need to improve; our future work will pursue harnesses that test against the requirement and verify completion claims, and training that rewards behavior on unseen cases.

AI Use Statement

We used generative AI tools for three tasks. First, to construct the benchmark, we used Codex with GPT-5.6 Sol to synthesize task materials from the analyzed source systems ( Section 4.1 ): the requirement documents, the development and held-out cases, and the task-specific Result rubrics. The authors designed each commission and reviewed and revised the generated materials. Second, AI agents assisted the trajectory analysis ( Sections 5.3 and H ) by labeling failure modes from builder trajectories, execution traces, and evaluator records; the authors reviewed the labels and the resulting counts. Third, we used AI assistants to aid and polish the writing of this paper. Coding agents and language models are also the object of study, acting as builders, runtime models, and judges ( Sections 5.1 and E ); this use is part of the method rather than assistance to the authors. We have reviewed all AI-assisted content and take full responsibility for the paper.

AgentSWE asks coding agents to build agents that execute code, access the web, and, in one Creation task, validate software vulnerabilities. All builder sessions and candidate executions run in isolated containers with pinned fixtures, and every model call passes through a benchmark-owned gateway ( Appendix D ). The benchmark involves no human subjects. Its tasks derive from public repositories and public benchmarks, used under their licenses and terms. Our analysis documents how coding agents misreport their own work, which we regard as a safety-relevant property of delegating software to them.

Section 4 and Appendices B and C describe the tasks, cases, and scoring. Appendices D and E give the evaluation infrastructure, builder instructions, model versions, effort settings, and budgets. Appendix F reports repeated runs and the variation of repeated evaluation, Appendix G lists per-run results, and Appendices H and I describe the analysis protocol and the traced cases. The benchmark, comprising the task packages, the development and held-out cases, the Creation and Editing rubrics and judge prompts, the evaluators, and the evaluation harness, is available at https://github.com/VectorSpaceLab/AgentSWE . Where an upstream license does not permit redistribution, the repository fetches the pinned upstream commit instead of including it. The repository also provides the eight tasks and the configuration of Table 5 as AgentSWE-Lite.

Appendix C Result Rubrics and a Worked Score

Each Result rubric scores the observable outcomes of its task. We describe two of them and reconstruct one recorded score.

PDF translation: content dominates presentation.

The six Result dimensions allocate 35 points to semantic completeness and terminology, 35 to fidelity of scientific objects and data, 12 to page and reading structure, 8 to alignment auditability, 8 to the offline viewer, and 2 to delivery integrity and accessibility, so 70 points concern the translated content. The evaluator checks the final bundle, the rendered pages and their geometry, and the viewer in a browser; source architecture earns no Result credit. A run that does not launch, exceeds a resource limit, or produces no parseable translated PDF scores zero. A valid but incomplete translation is still scored, under ceilings: omitting or leaving untranslated at least 25 % of the substantive units caps the total at 35, a material reversal of meaning caps it at 45, and repeated corruption of formulas or values caps it at 40. The lowest applicable ceiling bounds the sum of the dimension scores. A valid PDF without alignment and viewer artifacts is capped at 75, which separates missing functionality from execution failure.

OpenHands: outcomes, ceilings, and earned credit.

The dimensions are task completion (35), recovery quality (25), durable consistency (20), honest reporting (10), and privacy and scope (10). Each case lists numbered outcomes with observed facts, satisfaction flags, and safety flags. Unmet outcomes and safety failures impose ceilings on each dimension, and all applicable ceilings apply together.

Table 8 reconstructs the recorded score of GPT-5.6 Sol’s OpenHands delivery on test_002 . None of the five outcomes is satisfied: no missing chunk is uploaded, none of the three crash boundaries is reached, there are no remote commits and no local applies, no restart demonstrates durability, and the genuine event is not accepted. Four outcomes are safety requirements. The agent reports that it is blocked and acknowledges the unmet outcomes, which keeps some honesty credit. The score is 0 + 0 + 1 + 2 + 1 = 4 0+0+1+2+1=4 , although checkpoint and lease setup succeed.

Appendix H Behavioral Audit

H.1 Coverage and Counting Rules

The audit reads three kinds of evidence: the builder trajectory with the feedback it received, the frozen source or candidate diff, and the delivered agent’s held-out execution trace. A run is one builder on one task, as in Section 5.1 ; a case is one held-out input. A mode is present in a run if it appears in at least one case or in the builder trajectory, and modes can co-occur. Labels proposed with AI assistance were reviewed by the authors against these records. Where a report names a primary cause, it is the failure that cost the run the most points.

Creation covers the 270 held-out executions that record an execution trace (the desktop GUI task records none) and the final reports of the 42 builder runs that write one; the ten extended-budget runs are analyzed separately. Optimization covers the 25 development logs, the frozen candidates, and the builder trajectories. Editing covers the 33 runs that deliver a candidate ( Section H.3 ).

H.2 Creation: Validity Gates

Figure 11 gives the immediate outcome and execution time of each held-out execution. An error exit (nonzero exit code) can follow an implementation error, a failed self check, a rejected model response, or an external tool failure; a missing artifact follows from an earlier failure and is counted once.

Nearly half of the gate failures crash within one second, most of them from Qwen3.6 and the rest from the two GPT builders; neither DeepSeek builder crashes this way. Typical causes are input parsing and attempts to install dependencies into the submission directory, which the requirements forbid and the evaluator mounts read only. The other gate failures come after substantial execution, most often when the agent’s own check rejects its output and the agent reports the failure.

Executions that pass the gate can still miss the requirement. Of the 113 graded executions, 33 trigger at least one rubric ceiling, and in 15 the ceiling sets the final score. Document QA agents, for example, violate the output contract with repeated DOM target identifiers or unsupported CSS references. An agent that launches can still fall short of what it was asked to do.

H.3 Editing: Runs with a Delivery

The Editing analysis covers the 33 runs that deliver a candidate: DeepSeek-V4-Pro and GPT-5.5 on all ten tasks, GPT-5.6 Sol on nine, and DeepSeek-V4-Flash on four, with 198 held-out executions. The other runs deliver nothing to execute ( Section 5.2 ). Table 12 reports how many runs show each mode.

Capabilities of the third row can fail without any visible error: on one held-out case, an OpenClaw delivery issues 53 calls through its new handoff client and the product refuses every one, yet the execution passes the validity gates.

Development feedback names defects that survive freezing. Eight DeepSeek-V4-Pro runs receive feedback naming a violated cap identifier, and each of the eight still violates the same identifier on held-out cases. Nine of the ten DeepSeek-V4-Pro runs use all five submissions, so these defects survive with the submission budget spent.

Preservation failures differ from missing behavior. In 14 runs the delivered product permits a mutation it should refuse, such as repeating an operation that must run once or overwriting state it must preserve. These violations concern the regression obligation in Equation 2 .

H.4 Completion Claims

For Creation and Optimization the unit is the builder’s final report, including any completion summary written into the frozen artifact. We compare it with the actions the trajectory records, the files and capabilities the delivery contains, and the development feedback the builder received, and count a report as unsupported only when those records contradict it. A held-out failure by itself does not count against a report about development testing.

All nine unsupported reports assert completion. None of the 21 reports that admit partial completion or failure is contradicted by the record. Four of the six unsupported Creation reports assert that code works or was verified, while the trajectory shows that the code, or the path the report vouches for, never ran in its final form. GPT-5.6 Sol, for example, reports that its final repository-repair entrypoint emits the required reports for both development cases, yet the frozen file differs from every version the builder ran. The other two contradict feedback or audits the builder had already seen: Qwen3.6 calls its web-research agent complete and validated, with all citations resolving, one round after the judge scored both development cases 5 and reported no matching citations. In Optimization, DeepSeek-V4-Flash reports that two PinchBench tasks stayed at zero in every round, while its own development record shows one of them at 36 and 22, and it omits the four regressions it had recorded for the delivered round.

In Editing the speaker is the delivered agent, and its runtime claim is checked against effect logs, state, and output artifacts on each held-out case; a run counts if any case contains a contradiction, and 13 of the 33 runs that deliver do. On OpenHands test 006, for example, the agent describes a workspace commit as applied exactly once, while the world records zero local applies and the local manifest still lacks the file that exists only remotely. A completed entry in the effect log does not show that the workspace converged.

Appendix I Execution Case Studies

Cases 1–4 each trace one failure from feedback or runtime actions to the frozen artifact or the observed state; case 5 traces a repair that reaches the delivered agent. Quoted text is verbatim with omissions marked; structured records are condensed to the relevant fields.

1. A development score built on two hard-coded cases.

Qwen3.6’s Database analytics delivery is a single script of 2,073 lines that describes itself as “pure Python stdlib, no external dependencies” and never calls the runtime model. It classifies each request by phrases taken from the two development cases and dispatches to queries written for them:

Case type: "commerce" if the request contains “recognized net sales”, “decline by market”, […]; "adoption" if it contains “adoption”, “active_organization”, […]; otherwise none. Queries: _build_commerce_q1_sql […] _build_adoption_q3_sql , with the quarter bounds and the refund cutoff written in as constants.

Its development means climb from 38 to 99 over ten rounds and end at 96. The final feedback already points at the hard-coding:

Round 10, dev 001 (92/100): “ dashboard.html switches between literal Harbor/Mesa panels instead of deriving the selected rows, total, and largest negative category from submitted result data” […]

The held-out requests ask for other analyses over other databases. Five of them exit after 0.01 s with “Unknown case type: None”, the sixth with “no such table: organizations”, and all six fail the validity gate.

2. A higher development mean hides displaced failures.

DeepSeek-V4-Flash’s PinchBench run M09 adds playbooks for task categories and routes tasks to them by keyword. Its own assessment of round 2 records the tradeoff:

“Round 2: 76.5 (up from 72.8)” […] “But regressions: meeting tldr (97 → \rightarrow 0), spreadsheet (99 → \rightarrow 5), contract (100 → \rightarrow 62), syslog (36 → \rightarrow 22).”

Later rounds fall to 60.6, 63.7, and 51.65, so round 2 is frozen. Its held-out mean is 40.625 against the starter’s 55.825, with 7 wins, 17 losses, and 16 ties. The higher development mean already contains large regressions on other visible tasks, and selection still favors it.

3. Cancellation succeeds, and late work still changes state.

GPT-5.6 Sol’s OpenHands delivery runs pause, resume, and cancel on test_003 . The product observations and the burst probe record:

Lifecycle: pause → \rightarrow generation 2; resume → \rightarrow generation 3; cancel → \rightarrow generation 4, cancellation revision 5. Burst after cancellation: 80 callbacks accepted, 0 rejected; audit length 1 → 81 1\rightarrow 81 ; revision 5 → 85 5\rightarrow 85 ; event cursor 0 → 3320 0\rightarrow 3320 ; terminal state remains cancelled.

The commission requires those late callbacks to change nothing. The terminal state is correct, and the suppression fails: the audit log and the revision counter grow with every accepted callback. The agent’s report acknowledges the burst.

4. A final report describes a discarded revision.

The GPT-5.5 OSWorld run M20 selects round 3 (dev 40) after later rounds score 20 and 30. Its final report nevertheless describes harness changes:

“ run_harness.py provides BOM-tolerant input, deterministic JSONL output, atomic output/report writes, per-row agent mappings, and schema/length validation.”

The round 4 harness contains the BOM handling and the atomic writes. The frozen round 3 run_harness.py is byte-identical to the starter’s and contains neither; the round changes only the desktop policy. The report describes development work that the delivery does not contain.

5. A repair that reaches the delivered artifact.

For contrast, DeepSeek-V4-Flash’s BrowseComp run M06 answers a zero in the first round by finding a concrete protocol mismatch:

“All 50 rows scored 0 with valid contracts” […] “missing Authorization on model/search calls (the starter sent it on all calls)”.

The next candidate restores the header, broadens response parsing, and revises the research policy. Its development score reaches 34 and it stays selected through three further rounds. The frozen source contains the restored header, and the trajectory records a local check of the whole pipeline against a mock broker. Held-out performance rises from 18 to 46 ( S = 34.1 S=34.1 ). This repair fixes a fault the feedback exposed and reaches the delivered agent.

Appendix J Limitations

The main comparison and the harness studies build each pairing of builder and task once. Native Optimization objectives vary between repeated evaluations of the same agent ( Appendix F ), so individual Optimization results carry that variation. The development-case, prompt-prior, and eight-task studies use three independent builder runs per condition and report their differences descriptively.

Creation and Editing Result scores are assigned by a model judge ( Zheng et al., 2023 ) that applies the task rubric to the delivered artifacts and execution traces. Validity gates and rubric ceilings bound the judge’s discretion, but the scores still inherit its errors. The static source assessment of Section 5.3 uses the same judge. In both judged families, the judge shares a model family with at least one builder: GPT-5.6 Sol in Creation and DeepSeek-V4.1-Flash, beside DeepSeek-V4-Pro and DeepSeek-V4-Flash, in Editing.

Each task family fixes one runtime model and one judge ( Table 9 ), so absolute levels are comparable within a family but not across families. The development-case, prompt-prior, and extended-budget studies use DeepSeek-V4.1-Flash as builder, runtime model, and judge, and the extended-budget study also changes the case budget and the requirement ( Section E.2 ); each study is compared only within itself, not with Table 1 .
